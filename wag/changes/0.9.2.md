# 0.9.2 — The POC drafts the backlog, and standing up the app is a PBI

**From:** 0.9.1
**Date:** 2026-10-29

From VÖROOM, by voice and Sam. The business people should see the plan beside the POC, so
the backlog is now drafted and approved before the POC is built. And since `/wag:create-nextjs`
now follows each project's Architecture stack, standing up the app varies per project, so
it's no longer a fixed handoff step: it's the backlog's first PBI.

## What changed

- **A new Step 5, Draft the backlog** (`wag/workflows/poc.md`), between the Architecture
  (Step 4) and building the POC (now Step 6). Deploy is now Step 7 and the handoff Step 8.
  The user approves the backlog like the PRD and Architecture; the POC isn't built until
  they do.
  - **One file,** `.wag/docs/Backlog.md`, with its generated copy `.wag/poc/docs/Backlog.js`
    (the docs-copies rule now covers three docs).
  - **Init's principles:** business-outcome epics, vertical PBIs, full epics and PBIs from the
    templates, Epic 000, feature epics, Epic 501 Future. No status lines.
  - **A fixed shape** the page parses: `## Epic EEE — Name` then a one-line goal; `### PBI
    EEE.PPP — Title` then a one-line description; detail sections as `####`.
  - **Epic 000 always opens with three PBIs:** 000.001 Stand up the app (understand the POC
    and how it affects every PBI, then get the app running on the Architecture's stack, with
    `/wag:create-nextjs` as a reference, and create the git and GitHub repo); 000.002 Port the
    POC; 000.003 Run from dev, test from QA (Vercel link, env vars, first QA build;
    production out of scope). Each uses the latest version of every CLI it runs.
- **A PRD change carries through everything after it:** the Architecture, the backlog and
  the POC, with their docs copies regenerated.
- **Project Documents** (`wag/templates/poc/pages/project-documents.html`) has a Backlog
  section like the PRD and Architecture ones: note line, Download (`Backlog.md`), and three
  collapsible levels. Each epic shows its name and goal when closed, and each PBI its
  one-line description; open, each shows its detail.
- **The handoff (Step 8) no longer runs `/wag:create-nextjs` or creates the repo.** It copies
  `.wag/` to `~/source/<project>`, converts `Backlog.md` into WAG's epic folders
  (`epic-EEE-word/epic.md`, `PBI-PPP.md`), deletes `Backlog.md` from the copy, and finalises
  `.wag/` (init's Phase E). Then `/wag:adr` starts on PBI 000.001.
- **`wag/workflows/init.md`:** for a POC-origin project, Phase C is skipped (standup is PBI
  000.001) and Phase D uses the converted backlog. The three standard POC PBIs are the stated
  exception to "no infrastructure PBI".
- **`commands/wag/poc.md`** follows: the backlog step, no repo until PBI 000.001, three docs
  copies, and the new handoff.

Sorting the backlog by status belongs to the real app's in-app page later; it isn't built
here.

## Reconcile a 0.9.1 project

- **Detect:** a POC project with no `.wag/docs/Backlog.md`, or whose
  `pages/project-documents.html` has no `data-doc="backlog"` section.
- **Reconcile:**
  1. Draft `.wag/docs/Backlog.md` per Step 5, from the current PRD and Architecture and the
     POC as built, and generate `.wag/poc/docs/Backlog.js`. The user approves it.
  2. Update `pages/project-documents.html.md` from the starter's: add the
     `../docs/Backlog.js` script, the Backlog section, the backlog renderer in the script, and
     the `.doc h4` styles, keeping the project's own head and look. Then decode it.
  3. Redeploy if the POC is already deployed.
- **A project already handed off** on 0.9.1 keeps the backlog it was given.
- **Verify:** Project Documents shows the backlog, opened from disk, with each epic and PBI
  collapsing to its one line, and Download saves `Backlog.md`.
